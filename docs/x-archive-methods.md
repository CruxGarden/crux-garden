# Twitter/X archive preservation and local review

Reviewed November 10, 2026. The full account archive is the preservation baseline. X's [archive instructions](https://help.x.com/en/managing-your-account/how-to-download-your-x-archive) describe identity verification, requesting data, notification when ready and a ZIP download while logged in. Its [data-access explanation](https://help.x.com/en/managing-your-account/accessing-your-x-data) describes account information, posts, messages, relationships and media among the archive categories. This is broader than a post timeline, but does not prove that every referenced, deleted or inaccessible item is recoverable.

Open Settings and privacy → Your account → Download an archive of your data. Complete X's verification and request the archive; exact labels vary between its documented interfaces. When notified, download the ZIP in the authenticated browser. Keep the original package and all delivered parts, the data directory and the supplied archive viewer. In Migrate, select the downloaded folder or archive parts, review the explicit selection and preserve it. Requests, readiness checks and downloads remain manual; Migrate does not collect login cookies or automate private account endpoints.

## API alternative

X's [standard timeline documentation](https://docs.x.com/x-api/posts/timelines/introduction) limits a user's post timeline to the most recent 3,200 posts. A timeline is therefore not a substitute for the full personal archive or its messages/settings. API authorization, access entitlements and endpoint-specific limits require separate qualification. Migrate has no X API connector. No account registration or payment is needed for the local archive workflow.

## Implemented bounded review

After preservation, choose **Review export media**. The existing Node-owned background metadata worker streams script entries into a provisional bounded result, validates complete syntax and the preserved script's full SHA-256 before accepting any associations, maps candidates against receipt entries, and saves a separate report/SQLite summary. React and the existing host commands remain shared. Original scripts, archives and media are never modified or executed.

Recognized paths are `data/tweets.js`, older `data/tweet.js`, and `data/tweets-partN.js` / `data/tweet-partN.js` for positive N of up to six digits, optionally under a consistent wrapper folder. The literal envelope must be `window.YTD.tweets.partN =` or `window.YTD.tweet.partN =`, with the family and part agreeing with the filename; unnumbered files use part0. An optional initial UTF-8 BOM, bounded leading whitespace and one trailing semicolon are allowed. Only strict JSON array entries are parsed. Comments, expressions, calls, computed properties, unrelated assignments and trailing executable statements are refused. No eval, dynamic import, VM, script element or archive viewer is used.

The JSON must be an array of `tweet` objects with decimal string `id_str`. IDs are never converted to numbers. `extended_entities.media` is authoritative when present, otherwise `entities.media` is considered. An invalid authoritative container is reported rather than replaced with a partial alternative. Text-only posts are excluded from reference counts; repeated entries/references are retained, not merged.

Explicit `type: photo` records with the exact observed `https://pbs.twimg.com/media/<token>.<extension>` form are associated. Tokens use letters, digits, underscore and hyphen; supported extensions are jpg/jpeg/png/gif/webp. The candidate path is the exact `<post-id>-<token>.<extension>` within that archive's corresponding `data/tweets_media/` or `data/tweet_media/` directory. The CDN URL is inspected as text, never requested. Query strings, encoded paths, alternate hosts, userinfo, traversal and unfamiliar naming are unsupported. No basename search or normalization is used.

For `video` and `animated_gif`, each `video_info.variants` entry gets its own playback record. Exact `video/mp4` variants can associate `https://video.twimg.com/tweet_video/<token>.mp4` or `https://video.twimg.com/{ext_tw_video|amplify_video}/<numeric-id>/{pu|pr}/vid/[avc1/]<width>x<height>/<token>.mp4` with `<post-id>-<token>.mp4` in the same scoped media directory. Every listed variant remains visible, including absent higher-resolution versions; bitrate is not a preference or identity key. At most 32 variants per media entry are examined. HLS, query strings, encoded paths and unfamiliar forms are unsupported. Poster fields are never substituted for playback and remain in the original metadata; poster files are uninterpreted. Matches establish candidate filenames, not playability or original quality.

The shared resolver removes only Migrate's known archive-part namespace; wrapper roots must agree. Missing selected candidates stay unmatched and repeated paths across parts stay ambiguous. Captions and raw created_at text are bounded previews; no capture/publication-date correction is performed. Candidate paths are associations, not content identity or proof of current integrity. Use **Verify again** to check current media bytes; fingerprints remain the content comparison/deduplication authority.

## Primary format observations

The archive-tool author's [raw wrapper example](https://gist.github.com/lunasorcery/caeff957c35fb066e0a64b0bd90ade18) demonstrates wrapped tweet entries and extended_entities. The [cant-believe-its-not-twitter maintainer's archive handling](https://github.com/rrika/cant-believe-its-not-twitter/blob/main/db.py) distinguishes singular/plural data files and media folders and observes ID-prefixed media names. A [separate archive viewer implementation](https://github.com/kga1978/twitter-archive-viewer/blob/main/process_tweets.py) corroborates the post-ID/media-token association; Migrate uses exact names, not its substring fallback or network behavior. [TweetDuck's maintainer documentation](https://github.com/mizzy/tweetduck) records split `tweets-part1.js` inputs. These are observed formats, not a versioned X export specification. No third-party script is executed or installed; fixtures contain synthetic data.

## Playback evidence

The [archive maintainer's media store](https://github.com/rrika/cant-believe-its-not-twitter/blob/main/db.py) explicitly indexes ID-prefixed `.mp4` files, handles tweet_video and ext_tw_video/amplify_video URL tokens, and visits video_info variants separately from media_url_https. Migrate narrows that grammar and retains exact post/root scoping. The [other viewer author](https://github.com/kga1978/twitter-archive-viewer/blob/main/process_tweets.py) distinguishes photo previews from video/GIF variants, but selects the highest bitrate; Migrate reports variants separately. These firsthand implementations qualify candidate associations, not a guaranteed archive schema. X's [current API dictionary](https://docs.x.com/x-api/fundamentals/data-dictionary) is a separate API contract, not proof of local archive naming. The old v1 extended-entities URL redirected to the developer overview during this review. No downloaded third-party code was run.

## Bounds and gaps

X metadata now uses a shared streaming reader and array framer: 64 KiB IO buffers, 256 MiB per script, 1 GiB total script bytes, 256-byte envelope, 1 MiB per JSON entry, depth 128, 100,000 entries per script, and 30,000 derived records per review. The shared worker caps retained record encoding at 16 MiB and relationships at 100,000; the receipt remains limited to 32 MiB/20,000 entries and the full report to 64 MiB. The worker heap stays 256 MiB. Other provider adapters retain their existing 8 MiB sidecar/64 MiB aggregate input limits until separately qualified for streaming. The reader checks regular files, same opened file identity, size, timestamps, path replacement and SHA-256. No partial associations from a file survive a late syntax error, changed fingerprint, cancellation or exceeded budget. Failed-file originals stay preserved; other valid selected sidecars may still be reviewed. Aggregate input/record limits can stop the whole review.

UI previews remain 50 records, 10 candidate paths and 4096-character text fields. Pause stops between chunks; retry/restart rereads the script, not a saved mid-file cursor. Text-only posts are scanned but do not fill the reference report. The first larger fixture is about 9 MiB with 9,001 entries; this is not qualification at the 256 MiB limit or for a whole real account. Large individual records or unusually media-dense exports can still exceed bounds without altering originals.

Query-style CDN names, HLS/playlists/segments, old data/js layouts, messages, deleted-post files, likes, bookmarks, quoted/reposted source reconstruction, account metadata and missing-part detection remain uninterpreted. Keep and inspect the full archive; this is a media-reference check, not a complete post/media inventory. Export requests/downloads remain manual.

Engine tests cover executable-wrapper rejection, exact family/part matching, string ID precision, split-part collisions, safe paths, unsupported media, changed script hashes, malformed containers, caps, repeated references and restart. Browser/native/package evidence is in [verification](verification.md). No real X account/archive was accessed. Account completeness, large archive performance and real-export qualification remain pending.
