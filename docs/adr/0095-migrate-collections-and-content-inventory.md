# ADR 0095 — Selected cloud collections and persistent content inventory

Accepted 2026-11-10. Daniel requested automation for his own services, easiest to hardest; explicit file/folder selection; reusable method components; fingerprints in the database; local-versus-remote directory comparison; and deduplication to avoid downloading forgotten copies.

The first collection adapters are Bluesky public CAR/media, Amazon S3 objects, and Google Drive files/exports. A shared job engine owns explicit selection snapshots, discovery, per-file recovery, bounded streaming, safe publication and read-back verification. Adapters own listing/pagination, identity/revision checks, authentication and provider checksums. These are additional methods, not replacements for Dropbox shared links or local archive import.

Add an indexed `migrate_fingerprints` table through the existing API-owned SQLite adapter, never a second database owner. Record verified locations, SHA-256, available MD5, sizes, check time and optional source/version identity. Register new downloads and ordinary preservation outputs; explicitly selected directory scans bring older local files into the inventory. Rehash candidates before reuse and verify copied bytes again before publication. Only matching provider fingerprints or previously verified source/version identities establish reuse; names and sizes alone remain uncertain. Missing or changed locations do not count as present.

Deduplication in this increment avoids network transfers. Independent export copies remain separate files so editing one cannot alter another. Reject deletion-based cleanup and implicit hard-link storage deduplication. A later space-saving library must define immutable ownership and export portability first.

Google uses desktop PKCE/state plus an ephemeral loopback callback; credentials remain in memory, including refresh tokens for the current session. S3 uses explicit credentials and fixed AWS endpoints. Native hosts grant comparison/destination paths through pickers; local trusted API clients have equivalent authenticated operations. No automatic shell credential discovery, broad URL fetch, production fixture override or provider account mutation is added.

Collection recovery is file-level: finished files are rehashed, unfinished files restart. Do not mislabel it byte-range resume or infer a provider limitation. Dropbox's prior range checkpoints remain independently supported. Google registration and real S3/Google account acceptance remain pending; the user's live Bluesky public-record download succeeded. See `docs/cloud-services.md` and `docs/verification.md` for current evidence and limits.


November 10 implementation clarification: the shared checksum contract and API-owned catalog now additionally support Dropbox content hashes (SHA-256 over binary SHA-256 digests of 4 MiB blocks). Explicit scans and completed collection verification calculate it in one read with existing hashes. The nullable indexed column is additive; old entries need rescan, same-SHA writes retain a previously known Dropbox hash, changed-SHA writes clear it. This extends the existing provider-checksum decision rather than creating another transfer/store implementation. Independent vectors, database-upgrade and shared-worker fixtures qualify this foundation. Dropbox account OAuth/listing/download remains pending, as recorded in monorepo docs/dropbox-account-method.md.

## Selected local-file duplicate awareness — November 11, 2026

Extend the shared catalog to a read-only comparison of explicit local file-set inputs before preservation. Use the existing single worker lifecycle; the worker hashes files and requests bounded SHA-256/size candidates from the API owner, never opening SQLite. Rehash candidate bytes, exclude the same source path, retain stale/unreadable counts and identify results as dated observations with a bounded search. No automatic deletion, merging, skipped copies, new filesystem grant or storage owner. Pause/restart discards partial results; selection changes clear the optional saved summary. File/read/preview limits and validation are documented in docs/local-comparison.md. Folder/archive expansion is deferred until separately qualified.
