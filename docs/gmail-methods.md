# Gmail preservation and bounded mailbox inventory

Qualified against primary documentation November 10, 2026. This implementation uses synthetic files; Daniel's 16 GB mailbox and a real Google Takeout export have not been tested.

## Method choice

Use a full Mail Takeout export as the initial preservation baseline. Google's [Gmail export scope](https://support.google.com/mail/answer/10016932?hl=en) includes message content, headers, attachments, labels and settings. Deleted data cannot be recovered through this export. Encrypted messages stay encrypted, and managed accounts can restrict availability. Preserve the accompanying settings files even though the inventory does not interpret them.

In [Google Takeout](https://takeout.google.com/), deselect unrelated products, select Mail, inspect its inclusion options, then choose a one-time ZIP export delivered by email. Select all desired categories/labels; record those choices separately. Download every generated part before importing. A partial selection must remain visibly partial. Google's [download instructions](https://support.google.com/accounts/answer/3024190?hl=en) describe product selection, split archives and download delivery; changes during export creation may be absent. The same source documents `X-Gmail-Labels` as the exported label header. Its value is retained raw, not interpreted as an unambiguous comma-separated list.

Migrate does not request, poll for or download Takeout exports. Use its existing multiple-archive intake to preserve and unpack downloaded parts, folder intake for an unpacked export, or explicit-file intake for selected MBOX files. Explicit-file intake leaves selected archives opaque; choose archive intake to unpack them. The preservation receipt and SHA-256 catalog cover exactly the selected files. Review a small representative export before committing space/time for the entire mailbox. The original download, preserved copy and extracted archive contents may require substantially more disk space than Gmail's displayed storage figure; Migrate's actual review estimates the selected local work.

## API alternative, not yet implemented

The Gmail API can automate selective message retrieval. [messages.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) supports pagination up to 500 results, search queries, label filtering and explicit Spam/Trash inclusion. Listing yields identifiers; its result-size estimate is not a verified total. Label filters are an intersection and labels apply to messages, not necessarily entire threads.

[Message resources](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages) distinguish Gmail's immutable message ID, thread ID, internal date and label IDs from the complete base64url RFC-message bytes returned with RAW format. A future adapter should preserve those bytes alongside separate provider metadata and a label-name mapping; raw message bytes alone do not retain every API field. Do not deduplicate by subject, thread ID or an email's Message-ID header. Retain content hashes and source provenance.

Use the minimum read-only scope if implementing retrieval. Google's [scope documentation](https://developers.google.com/workspace/gmail/api/auth/scopes) classifies `gmail.readonly` as restricted; metadata-only scope excludes bodies. App registration/verification requirements depend on deployment. Existing Drive authorization does not establish Gmail access. Do not request broad send/delete permissions or claim public distribution qualification from fixture OAuth tests. No Gmail API connector, OAuth setup or account access is added by this slice.

## Implemented local review

After a Gmail import is preserved and verified, **Review mail inventory** runs in a bounded worker. Node remains the sole durable job/SQLite/fingerprint owner; React uses the same host-injected request interface. No additional library, daemon, database or account credential is required. Photo and mail reviews share safe receipt reads and the serialized background review lifecycle; format interpretation stays separate.

The worker opens only `.mbox` paths from the verified receipt, rejects symlinks and changed file identities, streams 64 KiB chunks and checks SHA-256 before including a file's derived counts/previews. It detects size/metadata changes during reading. It never modifies original or preserved files. Files with mismatched bytes are listed as invalid without exposing their unverified header previews. The original preservation receipt is not changed; each review creates a separate `mail-review-UUID.json` and stores a bounded summary in the job. No filename inside an email becomes a filesystem path.

Limits: at most 1,000 selected mailboxes, two million separator candidates per mailbox, a 64 KiB header block and a 64 KiB retained line prefix. Body lines may be longer and are streamed without retaining the full line. Reports retain at most 50 header previews per mailbox and 200 overall; UI summaries show at most 20 mailboxes and five previews each. Preview fields are shortened to 512 characters, with up to eight raw label-header values. Counts continue beyond the preview limit. Progress updates are throttled. Pause stops the worker cooperatively; retry starts review from the beginning, without repeating preservation. Saved running reviews become paused after restart.

A review includes candidate counts, format warnings, candidate counts with label headers, file SHA-256 and a bounded raw Subject/Date/Message-ID/label preview with byte offsets. Repeated IDs or overlapping label exports are not merged or deleted. Offsets and candidate counts are inventory aids, not extraction instructions or authoritative message identities. Non-MBOX settings and other files remain preserved and are listed as uninterpreted.

## Format limits and acceptance

[RFC 4155](https://www.rfc-editor.org/rfc/rfc4155.txt) explains that MBOX implementations vary in separator syntax, encoding and escaping. This inventory recognizes lines beginning with `From ` as candidates and ignores escaped `>From ` as separators. Unescaped body lines can still look like separators. Malformed/repeated identifying headers, missing header/body separators, oversized headers and content before the first separator are flagged. Content-Length variants are not interpreted. A zero-byte mailbox yields zero candidates; a nonempty file with no recognized separator is flagged through its preamble indicator.

The inventory is deliberately provisional even when there are no format warnings. It does not parse MIME, decode encoded-word subjects, count/extract attachments, render HTML, fetch remote images, normalize dates, reconstruct threads, restore labels, export individual messages or deduplicate them. Original mailbox bytes retain everything omitted from the summary. File-level fingerprints remain the content identity mechanism.

Fixture acceptance covers LF/CRLF, folded labels, repeated Message-ID values, encoded subjects, MIME-like attachment bytes, escaped and unescaped From lines, chunk-boundary separators, oversized header/body lines, report caps, changed/linked files, malformed receipt paths, cancellation/retry, SQLite restart, authenticated API access, browser embedding and desktop picker authority. A real Takeout export and sustained 16 GB-scale throughput remain unqualified. Compare a representative export with a trusted mail client before relying on message totals; never delete source mail based on this provisional inventory.
