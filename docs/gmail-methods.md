# Gmail preservation and bounded mailbox inventory

Qualified against primary documentation November 10, 2026. This implementation uses synthetic files; Daniel's 16 GB mailbox and a real Google Takeout export have not been tested.

## Method choice

Use a full Mail Takeout export as the initial preservation baseline. Google's [Gmail export scope](https://support.google.com/mail/answer/10016932?hl=en) includes message content, headers, attachments, labels and settings. Deleted data cannot be recovered through this export. Encrypted messages stay encrypted, and managed accounts can restrict availability. Preserve the accompanying settings files even though the inventory does not interpret them.

In [Google Takeout](https://takeout.google.com/), deselect unrelated products, select Mail, inspect its inclusion options, then choose a one-time ZIP export delivered by email. Select all desired categories/labels; record those choices separately. Download every generated part before importing. A partial selection must remain visibly partial. Google's [download instructions](https://support.google.com/accounts/answer/3024190?hl=en) describe product selection, split archives and download delivery; changes during export creation may be absent. The same source documents `X-Gmail-Labels` as the exported label header. Its value is retained raw, not interpreted as an unambiguous comma-separated list.

Migrate does not request, poll for or download Takeout exports. Use its existing multiple-archive intake to preserve and unpack downloaded parts, folder intake for an unpacked export, or explicit-file intake for selected MBOX files. Explicit-file intake leaves selected archives opaque; choose archive intake to unpack them. The preservation receipt and SHA-256 catalog cover exactly the selected files. Review a small representative export before committing space/time for the entire mailbox. The original download, preserved copy and extracted archive contents may require substantially more disk space than Gmail's displayed storage figure; Migrate's actual review estimates the selected local work.

## Selected account API alternative

The Gmail API can automate selective message retrieval. [messages.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) supports pagination up to 500 results, search queries, label filtering and explicit Spam/Trash inclusion. Listing yields identifiers; its result-size estimate is not a verified total. Label filters are an intersection and labels apply to messages, not necessarily entire threads.

[Message resources](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages) distinguish Gmail's immutable message ID, thread ID, internal date and label IDs from the complete base64url RFC-message bytes returned with RAW format. Migrate preserves those bytes alongside separate provider metadata and a label-name mapping; raw message bytes alone do not retain every API field. Do not deduplicate by subject, thread ID or an email's Message-ID header. Retain content hashes and source provenance.

Migrate requests the read-only scope for retrieval. Google's [scope documentation](https://developers.google.com/workspace/gmail/api/auth/scopes) classifies `gmail.readonly` as restricted; metadata-only scope excludes bodies. App registration/verification requirements depend on deployment. Existing Drive authorization does not establish Gmail access. Do not request broad send/delete permissions or claim public distribution qualification from fixture OAuth tests. The connector is now implemented with controlled network fixtures. Registration, actual consent and live-account acceptance remain pending.

## Implemented local review

After a Gmail import is preserved and verified, **Review mail inventory** runs in a bounded worker. Node remains the sole durable job/SQLite/fingerprint owner; React uses the same host-injected request interface. No additional library, daemon, database or account credential is required. Photo and mail reviews share safe receipt reads and the serialized background review lifecycle; format interpretation stays separate.

The worker opens only `.mbox` paths from the verified receipt, rejects symlinks and changed file identities, streams 64 KiB chunks and checks SHA-256 before including a file's derived counts/previews. It detects size/metadata changes during reading. It never modifies original or preserved files. Files with mismatched bytes are listed as invalid without exposing their unverified header previews. The original preservation receipt is not changed; each review creates a separate `mail-review-UUID.json` and stores a bounded summary in the job. No filename inside an email becomes a filesystem path.

Limits: at most 1,000 selected mailboxes, two million separator candidates per mailbox, a 64 KiB header block and a 64 KiB retained line prefix. Body lines may be longer and are streamed without retaining the full line. Reports retain at most 50 header previews per mailbox and 200 overall; UI summaries show at most 20 mailboxes and five previews each. Preview fields are shortened to 512 characters, with up to eight raw label-header values. Counts continue beyond the preview limit. Progress updates are throttled. Pause stops the worker cooperatively; retry starts review from the beginning, without repeating preservation. Saved running reviews become paused after restart.

A review includes candidate counts, format warnings, candidate counts with label headers, file SHA-256 and a bounded raw Subject/Date/Message-ID/label preview with byte offsets. Repeated IDs or overlapping label exports are not merged or deleted. Offsets and candidate counts are inventory aids, not extraction instructions or authoritative message identities. Non-MBOX settings and other files remain preserved and are listed as uninterpreted.

## Format limits and acceptance

[RFC 4155](https://www.rfc-editor.org/rfc/rfc4155.txt) explains that MBOX implementations vary in separator syntax, encoding and escaping. This inventory recognizes lines beginning with `From ` as candidates and ignores escaped `>From ` as separators. Unescaped body lines can still look like separators. Malformed/repeated identifying headers, missing header/body separators, oversized headers and content before the first separator are flagged. Content-Length variants are not interpreted. A zero-byte mailbox yields zero candidates; a nonempty file with no recognized separator is flagged through its preamble indicator.

The inventory is deliberately provisional even when there are no format warnings. It does not parse MIME, decode encoded-word subjects, count/extract attachments, render HTML, fetch remote images, normalize dates, reconstruct threads, restore labels, export individual messages or deduplicate them. Original mailbox bytes retain everything omitted from the summary. File-level fingerprints remain the content identity mechanism.

Fixture acceptance covers LF/CRLF, folded labels, repeated Message-ID values, encoded subjects, MIME-like attachment bytes, escaped and unescaped From lines, chunk-boundary separators, oversized header/body lines, report caps, changed/linked files, malformed receipt paths, cancellation/retry, SQLite restart, authenticated API access, browser embedding and desktop picker authority. A real Takeout export and sustained 16 GB-scale throughput remain unqualified. Compare a representative export with a trusted mail client before relying on message totals; never delete source mail based on this provisional inventory.

## Implemented account connector and bounds

The first account slice uses explicit individual messages or whole labels, plus an explicit All messages including Spam and Trash group. Selection starts empty; label selections form a union, with overlap resolved by immutable Gmail message ID within that account. Search queries, send/delete actions and attachment-only selection are not implemented. Selected label membership is resolved during discovery, not an atomic mailbox snapshot. Bound pages, repeated cursors and total discovered messages; stop rather than silently omit oversized/unsupported data.

Preserve decoded RAW response bytes unchanged as `messages/ID.eml`, with normalized provider IDs, internal date, history revision, selected label IDs/names and source account identity in the existing collection manifest. The latter is separate from the RFC message and includes per-file fingerprints. Read-only metadata revisions guard changes but never stand in for content hashes. Without a provider content checksum, new jobs must not skip downloads solely on message metadata. Completed same-job files continue to be rehashed for retry. Label names describe the connection's label snapshot; reconnect with changed names must not silently rewrite an existing plan.

Reuse the shared Google desktop PKCE callback, bounded request/token handling, cloud selection, jobs, provisional writes, free-space checks, fingerprints and persistence. Account identity is conservatively bound to the returned Gmail profile address; an address change cannot automatically resume an earlier source. The app requests only gmail.readonly, not Drive scopes, send/delete scopes or browser passwords. Raw JSON responses have an explicit size limit; no whole-mailbox body accumulation. Registration and real-account qualification remain pending. Fixture evidence is recorded in verification.md; it does not establish live-account or large-mailbox acceptance.


The root browser presents independent labels and an explicit All messages including Spam and Trash group; none are preselected. Entering a group lists 25 messages per page with shortened subject previews. Selecting a group includes matching messages beyond the current page, including matching Spam/Trash messages. Nested-looking label names remain independent labels, not recursive folders. One account's message ID appears once per job, even when selected through several labels; equal RFC Message-ID headers do not merge distinct Gmail messages.

Bounds are explicit: up to 10,000 labels per connection; 1,000 listing pages per selected group; 5,000 discovered messages and 16 MiB serialized provider metadata per job; 200 label IDs per message. Ordinary JSON/token responses are limited to 8 MiB. RAW responses allow 96 MiB encoded JSON and 64 MiB decoded mail. RAW JSON is buffered for one message at a time, not an entire mailbox; a large message can temporarily require several times its decoded size in memory. Oversized or malformed data stops with existing files intact. Use Takeout for messages outside these bounds. Per-file retries restart the interrupted message; byte-range resume is not implemented.

The metadata snapshot includes source address, Gmail message/thread IDs, historyId, internalDate and label IDs/names/types. Names describe the connection's label listing, not a live label-renaming feed. Metadata is checked before retrieval, against RAW response fields and again after the bytes are written provisionally. A changed plan requires a new selection. Snapshot hashes are revision guards, not content checksums. A changed source profile address cannot resume an old job; no claim is made that an email address is an immutable Google identity. [Profile documentation](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/getProfile) defines the returned address, and [label listing](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels/list) defines the ID/name/type listing. [Gmail formats](https://developers.google.com/workspace/gmail/api/reference/rest/v1/Format) distinguish metadata from raw base64url message bodies.

Credentials stay in memory. A new job downloads selected message bytes again because the provider supplies no trusted content checksum; completed files within a resumed job are rehashed before being accepted. The collection manifest binds provider metadata, paths and completed SHA-256 hashes. Review cloud export then uses the ordinary preservation workflow to preserve EML files and that manifest together. The MBOX inventory applies only to Takeout mailbox files and does not interpret these EML files. No full-account snapshot, incremental synchronization, settings export, label color restoration, classification-label export, attachment extraction or mail-client import is claimed.

## Google desktop registration and first real check

1. In Google Cloud Console, choose a project and enable the Gmail API. Drive API enablement alone is insufficient.
2. Configure Google Auth Platform branding and audience. For an external app in testing, add the account you will use as a test user. Add `https://www.googleapis.com/auth/gmail.readonly` to its data access configuration. Do not add send/modify/full-mail scopes for Migrate.
3. Create an OAuth client with type **Desktop app**. Copy the client ID and, if supplied, desktop client secret into Migrate's Gmail fields. These identify a public desktop client; they are not your Google password.
4. Choose **Connect Gmail**. Migrate constructs a Google browser authorization URL with PKCE and state, using the shared ephemeral loopback callback. Review the requested read-only Gmail access, then return to Migrate. [Google's desktop OAuth guide](https://developers.google.com/identity/protocols/oauth2/native-app) documents this flow. No registration is configured automatically by this implementation.
5. Start with a small label or a few messages including one attachment and one message carrying several labels. Choose an empty destination, download, inspect the manifest and open copies using a trusted mail application. Compare attachment bytes and Gmail details before scaling up. Migrate itself never renders HTML mail.
6. Restart Migrate and reconnect the same account before resuming a deliberately interrupted fixture/test job. Confirm completed messages are checked and original source mail is unchanged. Public distribution and managed-account policy acceptance need separate qualification; synthetic consent callbacks do not satisfy those checks.
